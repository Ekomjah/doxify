73: 
74: `doxify scout react 18 19 --repo /path/to/app` fetches release notes in the upgrade range, extracts breaking changes with exact quotes, and searches the tracked code for the affected APIs.
75: 
76: The point is not "here is everything that changed in React 19." The point is "here is the short list of changes that touch this repository, with file and line matches."

157: ## How I Built It
158: 
159: Doxify is a Python 3.10 CLI built with Typer, Rich, Pydantic, GitPython, Ollama, and the Sentry SDK. The default model is `gemma3:1b` running locally. Users who cannot or do not want to install Ollama can opt into Ollama Cloud with `--provider cloud` and `OLLAMA_API_KEY`; cloud mode defaults to `gemma4:31b` and warns that evidence cards will leave the machine.
160: 
161: The core pipeline is deliberately boring:
162: 
163: ```text
164: repo -> evidence cards -> 3 cards per section -> Gemma with [E#]
165:      -> deterministic verifier -> README / case study / defense / CI
166: ```
167: 
168: A 1B model cannot hold a whole repository. Doxify does not ask it to. It gives the model a small set of precise evidence cards and a citation grammar. The model turns those cards into prose. The compiler decides whether the prose is allowed to survive.
169: 
170: ### The compile loop
171: 
172: ```python
173: for spec in SECTION_SPECS:
174:     cards = retrieve_evidence(scan.evidence, spec, limit=3)
175: 
176:     if spec.id in {"snapshot", "problem", "reflection"}:
177:         generated = GeneratedSection(
178:             body=template_section(spec, cards),
179:             fallback_used=False,
180:         )
181:     else:
182:         generated = generate_section(
183:             client,
184:             spec,
185:             cards,
186:             repo_name=scan.repo.name,
187:             role=role,
188:             draft=draft,
189:         )
190: 
191:     section_claims = extract_claims(
192:         spec.id,
193:         generated.body,
194:         start_index=len(claims) + 1,
195:     )
196:     claims.extend(section_claims)
197: 
198: claims = verify_claims(claims, scan.evidence)
199: ```
200: 
201: Snapshot, problem framing, and reflection are deterministic templates because those sections are mostly structure. The narrative sections use the model. If the model fails, the section falls back to a template and the failure is recorded in the manifest.
202: 
203: ### The verifier
204: 
205: Every substantive sentence becomes a claim. A generated claim without a citation cannot pass. A citation to an evidence ID that does not exist is rejected.
206: 
207: ```python
208: if not claim.evidence_ids:
209:     claim.status = ClaimStatus.NEEDS_EVIDENCE
210:     claim.reason = "No citation token was found."
211:     return claim
212: 
213: cited = [evidence_by_id.get(evidence_id) for evidence_id in claim.evidence_ids]
214: unknown = [e for e, card in zip(claim.evidence_ids, cited, strict=False) if card is None]
215: if unknown:
216:     claim.status = ClaimStatus.REJECTED
217:     claim.reason = f"Unknown evidence citation(s): {', '.join(unknown)}."
218:     return claim
219: ```
220: 
221: The verifier also checks numbers against the cited evidence, checks code identifiers, checks token overlap, and flags claims that code cannot prove: deployment, "tests pass," OAuth, user counts, performance improvements, awards, team size, and "first/only" claims.
222: 
223: A sentence that says the repository has 30 records when the evidence says 26 is rejected. A sentence that says "reduced latency by 40%" without a measurement needs evidence. A sentence that says "deployed to production" needs human evidence; a deployment keyword in a config file is not enough.
224: 
225: ### README provenance
226: 
227: The visible README only gets supported material. The omitted claims stay in the compile session.
228: 
229: ```python
230: omitted = [
231:     claim for claim in claims
232:     if claim.status not in {ClaimStatus.VERIFIED, ClaimStatus.ATTESTED}
233: ]
234: ```
235: 
236: The hidden markers tell CI which evidence supports each section:
237: 
238: ```python
239: ids = " ".join(dict.fromkeys(card.id for card in cards))
240: if ids:
241:     lines.extend(["", f"<!-- doxify-evidence: {ids} -->"])
242: ```
243: 
244: That is how Doxify audits its own README. The repository has a committed evidence file, hidden markers, and a CI job that fails if a section is unmarked or unsupported. The self-audit currently reports five verified claims and eight author-attested claims.
245: 
246: ### Scout's exact-quote rule
247: 
248: ```python
249: def quote_in_notes(quote: str, body: str) -> bool:
250:     normalized = _normalize_quote(quote)
251:     return len(normalized) >= 12 and normalized in _normalize_quote(body)
252: ```
253: 
254: A breaking change whose quote is not found is dropped:
255: 
256: ```python
257: if note is None:
258:     warnings.append("Dropped a change because its quote was not found in the release notes.")
259:     continue
260: ```
261: 
262: Then the deterministic code search looks for the affected APIs in tracked files, with word-boundary matching so `render` does not match `renderToString`:
263: 
264: ```python
265: pattern = re.compile(rf"(?<![A-Za-z0-9_$]){re.escape(alias)}(?![A-Za-z0-9_$])")
266: ```
267: 
268: Scout is a candidate finder, not a type checker. It tells you where to look. It does not promise the migration is complete.
269: 
270: ### SerpApi
271: 
272: Scout prefers an explicit `--notes` file, then GitHub releases, then SerpApi. The fallback searches for release-note pages and pulls their text. The exact-quote rule still applies, so a search result cannot become a confident breaking-change claim unless the quote is actually on the page.
273: 
274: ```python
275: key = serpapi_key or os.environ.get("SERPAPI_API_KEY")
276: if key:
277:     notes = fetch_serpapi_notes(package, from_version, to_version, api_key=REDACTED
278:     warnings.append("Used SerpApi because GitHub release notes were unavailable.")
279: ```
280: 
281: No key means the user can still pass `--notes FILE` and stay offline. When the key is used, the HTTP span records only the scheme, host, and path, so the query string and API key do not leak into Sentry:
282: 
283: ```python
284: return f"{parsed.scheme}://{parsed.netloc}{parsed.path}"
285: ```

287: ### Sentry Agent Tracing
288: 
289: A local CLI has a visibility problem: the user sees a spinner, not the pipeline. Sentry gives Doxify an opt-in view of what happened without turning the tool into a data collector.
290: 
291: ```python
292: init_monitoring()
293: command = _command_name()
294: with command_transaction(command):
295:     app()
296: ```
297: 
298: Inside the Ollama client, a model call becomes a span with provider, model, temperature, max tokens, latency, and token usage. The prompt and the output are not recorded.
299: 
300: ```python
301: with model_span(
302:     provider=self.provider,
303:     model=self.model,
304:     temperature=temperature,
305:     max_tokens=num_predict,
306: ) as span:
307:     response = self._client.chat(**payload)
308:     record_model_usage(
309:         span,
310:         prompt_tokens=prompt_tokens,
311:         completion_tokens=completion_tokens,
312:     )
313: ```
314: 
315: The trace looks like this:
316: 
317: ```text
318: doxify.compile
319: ├── validate
320: ├── scan
321: ├── generate × 6
322: │   └── model.chat  (provider, model, tokens, latency)
323: ├── verify
324: ├── defense
325: └── export
326: ```
327: 
328: When a compile is slow, the trace says whether the time went into scanning, the model, or verification. When Scout fails, the HTTP span shows which fetch failed without exposing the URL query string.
329: 
330: Monitoring only initializes when `SENTRY_DSN` is set, and `DOXIFY_SENTRY=0` turns it off. The SDK uses a restricted data collection policy:
331: 
332: ```python
333: SAFE_DATA_COLLECTION = {
334:     "user_info": False,
335:     "cookies": {"mode": "off"},
336:     "http_headers": {"request": {"mode": "off"}},
337:     "http_bodies": [],
338:     "url_query_params": {"mode": "off"},
339:     "graphql": {"document": False, "variables": False},
340:     "gen_ai": {"inputs": False, "outputs": False},
341:     "database_query_data": False,
342:     "queues": False,
343:     "stack_frame_variables": False,
344:     "frame_context_lines": 0,
345: }
346: ```
347: 
348: Tokens, API keys, and absolute home paths are redacted before events leave the process. `before_send`, `before_breadcrumb`, `before_send_transaction`, and `before_send_log` all pass through the same policy.
349: 
350: `self-check` can also use a Sentry cron monitor:
351: 
352: ```python
353: with cron_monitor(monitor_slug):
354:     result = run_self_check(client=client)
355: ```
356: 
357: The monitor config describes a nightly 3 a.m. UTC check-in with a 10-minute margin and a 15-minute maximum runtime. `.github/workflows/sentry-nightly.yml` runs `doxify self-check` on that schedule, so a broken install shows up as a missed check-in.

365: ```yaml
366: - name: Verify self-audit README

387: ### What broke along the way
388: 
389: **The first case study was too confident.** The run against the local demo repo left 34 of its 47 claims needing evidence. That is exactly the kind of fluent, vague writing I was trying to avoid. The fix was not a longer prompt. It was smaller evidence sets, deterministic templates for structural sections, and a review queue that shows every unresolved claim.
390: 
391: **The README writer could overwrite an existing file.** It now refuses without `--force` and backs up the old file when it does.
392: 
393: **Sentry's defaults are built for web apps, not private repositories.** They collect more than a local CLI should. Request bodies, headers, query strings, user info, and model inputs are now explicitly off. Tokens and paths are redacted. A monitoring feature that leaks the repository is worse than no monitoring.
394: 
395: **A passing CI check proves very little if it cannot fail.** The verify job includes an unresolved case study that is expected to fail. If it ever passes, the job fails.
396:

403: ## Why Does Open Innovation Matter?
404: 
405: Four things were possible because the pieces are open:
406: 
407: - **The repo can stay private.** A developer with an NDA or sensitive customer data cannot upload the code to a hosted writing tool. Local Gemma means the evidence does not go to a model API.
408: - **It runs on a normal laptop.** The same weak CPU that almost kept me out is enough for `gemma3:1b`, which is about 806 MB. After the model download, the default workflow is offline. No API key, no per-token bill.
409: - **The model is a flag.** `--model` or `DOXIFY_MODEL` can swap Gemma for another Ollama model without changing the verifier.
410: - **The verifier is inspectable.** You do not have to trust the model or trust me. The checks are in the repo, and the evidence is in the output.
411: 
412: The optional services do not change that. Sentry is off without a DSN. SerpApi is a fallback; `--notes FILE` keeps Scout offline. The GitHub Action runs the same local verifier.
413: 
414: Cloud mode exists for people who cannot install Ollama, but it is opt-in and warns that evidence cards leave the machine. The default stays local because privacy is the feature.
415: 
416: A sloth should not have to choose between a useful tool and a private repository.
